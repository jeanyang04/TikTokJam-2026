## The short version

Zeon built the middle of the chain and both ends are missing. Nothing can run end to end today,
and no single person can fix that alone.

The demo chain is: mint a RunToken + agent JWT (B1) → project it into Codex args (B2) →
container reaches the gateway (B2) → gateway checks and denies (Zeon, **done**) → card and
decide routes (B1) → UI shows it (F). Links 1, 2, 3, 5 and 6 are absent. Link 4 is complete
and well tested and currently has no way to be reached by a real agent run.

## Risks, worst first

**1. The runtime image pins the wrong Codex.** `Dockerfile.runtime:4` still says
`CODEX_VERSION=0.111.0`. CLAUDE.md and TEAM.md both rest the entire transport decision on
"verified: codex 0.144.6 sends `-c mcp_servers.*.http_headers`". B2's Day 1 item 1 was to bump
it and re-confirm from inside the image. Until that happens, the assumption the whole
architecture depends on is untested against the version actually installed. If the header does
not survive, the fallback is the REST shim (`POST /gw/:tool`, TEAM.md line 36), and that
decision gets more expensive every hour it waits.

**2. `ARK_API_KEY` is in the container today.** `container-codex-runner.ts:72` passes it
through `--env` and `:240` puts it in the child environment. CLAUDE.md non-negotiable #4 says
secrets never enter the container. This is a rule violation on `main` right now, not a pending
ticket, and it is exactly what a judge checking the stated rules against the code will find.
The removal is meant to sit behind `LLM_PROXY_ENABLED`, which does not exist in `config.ts`.

**3. No RunToken is ever minted.** `agent-service.ts:157` `sendMessage()` creates the run and
the message and calls `executeRun`, with no RunToken row and no agent JWT (ticket 04). This is
the keystone: without it the gateway cannot be exercised by a real run, so Day 1's 18:00 gate
("one real container makes one denied tool call that appears in the store") cannot pass. When
it lands, `RunToken.scp` must come from `effectiveScopes(agent)` (SEAMS.md line 75) or
"Allow for this run" dies silently on the follow-up message.

**4. LOCK 2 does not exist.** No `db.ts`, no `redact.ts`, no `apps/server/migrations/`, no
Postgres service in `docker-compose.yml`, no `rls.test.ts`. The gateway's `crm_read`/`crm_write`
answer "CRM resource unavailable" by design until `withOwner` is passed in `index.ts`. Half the
protected-resource story is missing, and `redact.ts` is a stated requirement for every RunEvent
(the gateway ships its own redactor behind `setRedactor`, so audit rows are redacted today,
just not by B3's pattern list).

**5. `GATEWAY_ENFORCE=false` turns LOCK 1 into a pass-through.** `index.ts:32` reads it, and
`gateway.ts:126`/`:134` skip the grant and IFC checks when it is off. It is undocumented in
`.env.example`, which is the only thing keeping it from being a footgun. Decide whether it
survives into the submission; an env var that disables the security control is a bad look in a
security track even when it defaults to on.

**6. `.env.example` is stale.** It lists none of `JWT_SECRET`, `SEED_USERS`, `GATEWAY_ENFORCE`
or `LLM_PROXY_ENABLED`. A judge cloning fresh gets the dev-default JWT secret without being
told. B3's Day 2 item.

**7. Scene 2 has neither path.** `/demo/replay` exists only as a stub inside `auth.test.ts:131`.
The live path needs the chain above; the fallback needs B2 to write the route. Right now the
committed, non-cuttable IFC scene has no way to be shown, even though `ifc.ts` itself is built.
